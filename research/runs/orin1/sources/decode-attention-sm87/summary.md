# NVIDIA-family decode-attention kernels for Ampere (sm_80/86/87) and what they imply for Orin sm_87

Research date: 2026-10-23. Target: Jetson AGX Orin 64GB (sm_87, GA10B, 16 SM × 128 CUDA cores, 1.3 GHz, 204.8 GB/s LPDDR5, 4 MB L2). Workload: batch-1 decode, GQA 24:4 (g=6), head_dim=256, paged KV (16/32/64/128), fp8 e4m3 / packed fp6 e2m3, L=4K–128K, split-KV. Baseline kernel: scalar-FMA GEMV, 64 CTAs × 96 threads (128 launched, 96 active), 2-stage cp.async, ~18 GB/s effective, 8.3% achieved occupancy. Competitor: FlashInfer 0.7.0.post1 decode ~4–5×.

Companion artifacts already in this repo: `task/research/orin-flashinfer-decode/summary.md` (FlashInfer/vLLM routing + CC 8.7 specifics) and `task/research/arxiv-orin-decode-attention-kernel.md` (papers). This file covers the NVIDIA/open-source **kernel structures** (read from source) + Orin memory-system facts, and ends with the ranked mechanism list.

Method note: the web search engine returned empty results for the whole session (8/8 queries, including trivial ones — see Methodology); all reading was done via `github_*` tools, direct source fetches, and `web_md` on known primary URLs.

## A. What NVIDIA's own kernels actually do (read from source)

### A1. FlashInfer 0.7.0.post1 — both decode paths (the baseline to beat)

GEMV path (`include/flashinfer/attention/decode.cuh`): `vec_size = max(16/sizeof(DTypeKV), HEAD_DIM/32)` → **16 for fp8 hd256**; `bdx = 16` threads per K row; `bdy = GROUP_SIZE = 6`; `num_threads = max(get_heuristic_num_threads(g, sizeof), bdx*bdy)` where the heuristic returns 128 for g≠8 → **128 threads launched (bdx*bdy=96 active), bdz=1** ([decode.cuh](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/include/flashinfer/attention/decode.cuh)). Note this corrects the prior summary's "96 threads": 128 are launched, 96 used. Split-KV (`seq_len > 256`): `max_grid = occupancy × num_SM`, `kv_chunk_size = max(ceil(L / (max_grid/num_kv_heads)), 256)` — i.e. **one full wave of CTAs, min 256-token chunks**, then a separate merge kernel ([decode.cuh](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/include/flashinfer/attention/decode.cuh)). Per-token iteration granularity: with `tile_size_per_bdx = 1` for GQA, each cp.async stage covers **one KV token = 512 B (K+V, fp8 hd256)** — this is structurally the same granularity problem as our 18 GB/s kernel.

TC path (what vLLM 0.32.0 actually uses on Orin — `use_tensor_cores=True` unconditional, see companion summary): `FA2DetermineCtaTileQ(packed_qo_len, ...)` returns **CTA_TILE_Q = 16 for avg_packed_qo_len ≤ 16** ("decode / speculative decode: lean CTA16, 1x4 warp layout") ([utils.cuh](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/include/flashinfer/utils.cuh)) — i.e. **the 6 GQA q-heads are packed into the 16-row M dimension of `mma.m16n8k16`** with 1 Q-warp + 4 KV-warps (128 threads); NUM_MMA_KV is chosen from `max_smem_per_block_optin` so 2 CTAs/SM fit ([prefill.cuh](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/include/flashinfer/attention/prefill.cuh)). fp8 KV is staged in smem fp8 (128B swizzle), converted in registers by software `fast_dequant_f8f16x4` before every HMMA (no HW fp8 cvt/mma before sm_89) ([vec_dtypes.cuh](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/include/flashinfer/vec_dtypes.cuh)).

### A2. FlashAttention-2 split-KV decode (sm_80, bf16/fp16 KV only)

`run_mha_fwd_splitkv_dispatch`: **kBlockM=64, kBlockN=64 for hdim256, 4 warps = 128 threads** ([flash_fwd_launch_template.h](https://github.com/Dao-AILab/flash-attention/blob/main/csrc/flash_attn/src/flash_fwd_launch_template.h)). KV loads use `SM80_CP_ASYNC_CACHEGLOBAL<cute::uint128_t>` = **16-byte cp.async.cg, 8 elements/thread** ([kernel_traits.h](https://github.com/Dao-AILab/flash-attention/blob/main/csrc/flash_attn/src/kernel_traits.h)). Split heuristic ([flash_api.cpp](https://github.com/Dao-AILab/flash-attention/blob/main/csrc/flash_attn/flash_api.cpp)): if `batch×heads×mblocks ≥ 0.8×num_SMs` → 1 split; else choose the smallest split count with wave-efficiency ≥ 0.85×best, capped at 128 splits and `num_SMs = num_sm×2`. Combine kernel: separate launch, `kBlockM = 4` for hdim%128==0 (256→4), grid over `b*h*seqlen_q`, log2-dispatched by split count ([flash_fwd_launch_template.h](https://github.com/Dao-AILab/flash-attention/blob/main/csrc/flash_attn/src/flash_fwd_launch_template.h)). **Critical GQA fact: FA2-Ampere does NOT pack query heads into M** — grid.z covers all `h` q-heads and K/V are indexed `bidh / params.h_h_k_ratio` ([flash_fwd_kernel.h](https://github.com/Dao-AILab/flash-attention/blob/main/csrc/flash_attn/src/flash_fwd_kernel.h)): each of the 6 q-head CTAs per kv-head re-streams the same KV, relying on L2 to absorb it. Head-packing (`pack_gqa`) is an FA3/Hopper feature.

### A3. CUTLASS example 41 (Ampere fused FMHA, forward)

GEMM-based FMHA: **32 queries × 128 keys per block, 4 warps (128 threads)** for head_size > 64; warp budget 16 warps/SM on CC≥8 (→ 4 CTAs/SM); QK^T and PV run as CUTLASS tensor-op GEMM pipeline stages (`mma_multistage`/`mma_pipelined`, `mma_tensor_op_*` iterators) with smem staging and swizzle ([kernel_forward.h](https://github.com/NVIDIA/cutlass/blob/main/examples/41_fused_multi_head_attention/kernel_forward.h), [fused_multihead_attention_fixed_seqlen.cu](https://github.com/NVIDIA/cutlass/blob/main/examples/41_fused_multi_head_attention/fused_multihead_attention_fixed_seqlen.cu)). **No split-KV/decode variant exists in CUTLASS for Ampere** (checked: no split-k in ex41; split-KV FMHA examples are Hopper 88 / Blackwell 77). NVIDIA's Ampere decode references are TRT-LLM (below) and the flash-decoding scheme itself ([pytorch.org blog](https://pytorch.org/blog/flash-decoding/)).

### A4. TensorRT-LLM: classic MMHA + XQA

Classic `masked_multihead_attention_kernel` ([decoderMaskedMultiheadAttentionTemplate.h](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/kernels/decoderMaskedMultiheadAttention/decoderMaskedMultiheadAttentionTemplate.h)): `THREADS_PER_BLOCK ∈ {64,128,256}`, **`__launch_bounds__(256, MIN_BLOCKS_PER_SM=4)`** for fp16/fp8 (3 for fp32) — i.e. NVIDIA pins ≥4 CTAs/SM at 256 threads; QK dots use `mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32` (`hmma_fp32`) with `THREADS_PER_KEY`-lane cooperation; KV cache layout `[B,H,Dh/x,L,x]`, x=16 for fp8 (transposed K rows so a 16-byte vector spans the head dim); fp8 memory vectors are `fp8_4_t` (4×8-bit) but compute vectors are `float4` (dequant on load); 16-byte `Qk_vec_m` for all dtypes ([mmha_notes.md](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/kernels/decoderMaskedMultiheadAttention/mmha_notes.md)). Multi-block (split-KV) grid setup: `blocks = min(divUp(SM×blocks_per_sm, batch×heads), …)`, `seq_len_per_kv_loop = divUp(block_size/threads_per_value) × 8` (unroll 8) ([decoderMaskedMultiheadAttentionLaunch.h](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/kernels/decoderMaskedMultiheadAttention/decoderMaskedMultiheadAttentionLaunch.h)).

XQA (the newer GQA/MQA decode kernel, [blog](https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/blogs/XQA-kernel.md)): support gate `supportConfigHMMA` requires **SM ≥ kSM_80**, fp16/bf16 compute, **fp16/bf16/int8/e4m3 KV cache**, head_size 16–256, **`head_grp_size × beam_width ≤ 32`** (query rows packed into the M dimension), paged tokens_per_block ∈ {16,32,64,128} ([kernelUtils.cpp](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/kernels/decoderMaskedMultiheadAttention/decoderXQAImplJIT/kernelUtils.cpp)). Launch grid `dim3{specDecBlocks, multiBlock, kv_heads×batch}`; spec-dec blocks = `divUp(qSeqLen, 64/numQHeadsOverKV)` ([decoderXQARunner.cpp](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/kernels/decoderMaskedMultiheadAttention/decoderXQARunner.cpp)). Multi-block count heuristic ([decoderXQARunnerUtils.h](https://github.com/NVIDIA/TensorRT-LLM/blob/main/cpp/tensorrt_llm/kernels/decoderMaskedMultiheadAttention/decoderXQARunnerUtils.h)): `historyLength/128` initial, capped by `sqrt(8×that)`, then adjusted so `batch×kv_heads×blocks/SM_count ≈ kTargetWaveFactor = 8` waves; spec-dec variant populates **at most 1 wave** and only tunes when the wave is empty. **The Ampere XQA HMMA kernel source is not public** (ships as NVRTC/cubin; only the runner is in-tree) — a verified gap. Published XQA result: Llama-70B FP8 H200, 1,227 → 2,941 tok/s/GPU (2.4×) with the same latency budget ([XQA blog](https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/blogs/XQA-kernel.md)).

### A5. llama.cpp (current main)

Three kernels with a measured dispatch policy ([fattn.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/fattn.cu)):
- **MMA kernel (`fattn-mma-f16.cuh`)** — tensor cores with **GQA packing**: the CTA tile covers `ncols1 × ncols2` queries where `ncols2` = GQA group size padded to {1,2,4,8,16,32} and `ncols1 = 64/ncols2`; for **DKQ=DV=256 on Ampere: 128 threads, occupancy 2 CTAs/SM, `nbatch_fa` = 32–64 KV rows per MMA step, `nbatch_K2/V2` = 128 rows staged (double-buffer), `Q_in_reg`** ([fattn-mma-f16.cuh config table](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/fattn-mma-f16.cuh)). For g=6, the `gqa_ratio > 4` branch picks `ncols2 = 8` — i.e. **pad 6 q-heads to 8 columns** rather than 16.
- **Vector kernel (`fattn-vec.cuh`)** — 128 threads, no smem, scalar-FMA with 16-byte loads; chosen for `Q->ne[1]==1` single-token decode on Ada+ and when GQA packing doesn't apply ([fattn.cu](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/fattn.cu), [fattn-vec.cuh](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-cuda/fattn-vec.cuh)).
- Tile kernel for prefill. Note the GQA-opt requires 16B-aligned strides; the vec kernel has no tensor cores at all.

### A6. Flash-Decoding (the split-KV canon)

Batch-1 decode on FA2 uses <1% of an A100; the fix is a new parallel axis over KV: split KV into chunks, run partial attention with per-split LSE, then a small reduction kernel — "up to 8× faster generation," attention 50× faster than FA2 at 64K+, near-constant runtime to 64K ([pytorch.org/blog/flash-decoding](https://pytorch.org/blog/flash-decoding/)). This is the shared skeleton of every kernel above; the differences are tile shapes, packing, and merge placement.

## B. Orin (sm_87 / GA10B) memory-system facts

- **Theoretical 204.8 GB/s** (LPDDR5 256-bit, 3200 MHz) — [Jetson AGX Orin Technical Brief](https://www.nvidia.com/content/dam/en-zz/Solutions/gtcf21/jetson-orin/nvidia-jetson-agx-orin-technical-brief.pdf) (local copy: `task/research/orin-board-matrix/agx-orin-techbrief.txt`).
- **No ECC on the AGX Orin 64GB dev kit** — NVIDIA's own spec table lists ECC only for the AGX Orin Industrial variant ("Inline DRAM ECC Supported") ([Jetson Orin page](https://www.nvidia.com/en-us/autonomous-machines/embedded-systems/jetson-orin/#tech-specs), archived in `task/research/orin-board-matrix/nvidia-agx-orin-page.md`). So no ECC bandwidth tax on the dev kit.
- **Sustained STREAM-class bandwidth: expect 60–80% of theoretical** (122–164 GB/s); causes: DRAM refresh, command/address overhead, controller arbitration, ECC/protocol; 16-byte vectorized loads + unroll are the reference kernel shape; contended CPU+GPU runs total ~70–80% ([jetson-mem-bench guide](https://github.com/jetsonhacks/jetson-mem-bench/blob/main/docs/GUIDE.md)).
- **Unified-memory contention is real**: CPU and GPU share the LPDDR5 bus; contended runs are a first-order effect (jetson-mem-bench solo-vs-contended methodology) and decode throughput drops as sequence length grows on Orin AGX ([Arya & Simmhan, 2506.09554](https://arxiv.org/html/2506.09554v1)).
- **ncu clock control does NOT work on GA10b (Orin)**: "On Linux (aarch64 sbsa), clock control is not supported with Nsight Compute for the following GPUs: GA10b (Orin), GB10b (Thor)"; "on mobile targets (L4T) there may be variations in profiling results due the inability for the tool to lock clocks"; NVIDIA's fix: **`jetson_clocks` to lock clocks externally + `--clock-control none`** ([Nsight Compute Profiling Guide §Clock Control](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#clock-control)). So ncu numbers on Orin are taken under whatever DVFS state the GPU is in — base-clock locking cannot be the confound (it can't be applied); **uncontrolled DVFS is**.
- **L2 residency management is supported on all CC 8.x** (access-policy-window / evict hints) ([CUDA guide §L2 Cache Control](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/l2-cache-control.html)); PTX-level: `ld.global.L2::evict_first/evict_last`, `.level::prefetch_size` 64B/128B/256B, `createpolicy` fractional/range policies, `cp.async` with `.level::cache_hint` ([PTX ISA §Cache Eviction Priority Hints](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-cp-async)). `cp.async.cg` with 16 B bypasses L1 and caches in L2 — the universal KV-load idiom in all four kernels above.
- **Read-vs-write asymmetry on LPDDR5: NOT verified** (no accessible primary source found this session; flagged in Gaps). Directionally: decode attention writes only O/partials (negligible bytes), so the read stream is the only path that matters; the contended-bus effect above is the measurable unified-memory risk.

## C. Ranked mechanisms: 18 GB/s → >100 GB/s on sm_87

Expected-impact ratings are derived from the roofline: per layer per step, fp8 KV bytes = 4 heads × L × 512 B (L=32K → 64 MB; L=128K → 256 MB). At 18 GB/s that's 3.6–14.9 ms; at 120–150 GB/s it's 0.4–2.1 ms. Scalar-FMA compute (QK+PV ≈ 3.2 GFLOP at L=128K → ~0.6 ms at 5.3 TFLOPS, plus ~268 M software fp8→fp32 conversions) is comparable to the memory time — i.e. the current kernel is *not* compute-bound at 18 GB/s; it is latency/occupancy-bound (8.3% achieved of a 25% resident-warp ceiling). Every mechanism below is about keeping enough bytes in flight.

### 1. Stage ≥64 KV rows per smem stage (not 1 token per iteration) — impact: ★★★★★, effort: medium
All fast kernels process 32–128 KV rows per smem stage: FA2 hdim256 kBlockN=64 (4 warps); FlashInfer TC decode NUM_MMA_KV=2 → 128 rows/iter; llama.cpp nbatch_fa=32–64 with 128 rows double-buffered; XQA paged blocks up to 128 tokens. A 1-token (512 B) stage per CTA with a 2-stage ring cannot keep enough requests outstanding to cover LPDDR5 latency; 64 rows × 256 B = 16 KB per stage per buffer, 2–4 stages, is the shape every reference uses. Orin's 163 KB/block smem (CC 8.7, not the 100 KB of sm_86/89) makes 3–4 stages of 32 KB tiles feasible at 1 CTA/SM, or 2 CTAs/SM with 2 stages (FlashInfer's budget: 2 CTAs/SM ≈ 84 KB cap → NUM_MMA_KV=2). Sources: A1, A2, A5, companion summary Q5.

### 2. Pack the 6 GQA q-heads into the MMA M dimension (mma.m16n8k16, pad 6→16 rows) — impact: ★★★★★, effort: medium-high
QK^T for batch-1 GQA is 6 × 256 × L — a thin matrix-vector set. Every fast GQA decode kernel pads the group into one M-tile and reads KV **once**: FlashInfer CTA_TILE_Q=16 for packed_qo_len ≤ 16 (1 Q-warp + 4 KV-warps); XQA packs `head_grp × beam ≤ 32` rows; llama.cpp pads g=6 to ncols2=8 (its 8-column config: 128 threads, 2 CTAs/SM for hd256). The padding rows are zero-work (no extra KV traffic); the win is 4× HMMA issue-rate vs FP32 FMA (1024 vs 256 FLOP/clk/SM-class) plus a much shorter dependency chain, and — decisively on a bandwidth-bound part — **KV bytes are read once per group instead of 6×** (FA2-Ampere's per-q-head CTAs multiply logical KV traffic 6× and lean on L2; at 4 MB L2 vs 256 MB KV, that reliance is exactly what you don't want on Orin). The "pack 6×16" pattern asked about in Q2 exists: it is FlashInfer's CTA_TILE_Q=16 (6 rows + 10 padding), and llama.cpp's pad-to-8 variant. Counter-evidence: FlashDecoding++'s pad-to-8 argument (M=16 native mma row-pair; don't pad to 64) and FlashInfer keeping the GEMV for M=1 in its API default — at g=6 hd256 the TC path still wins because 6 rows > 1 (see companion arxiv summary: M=1 GEMV +22% on A100, M=4 TC 2×).

### 3. Fill the machine: 128–256 threads/CTA, ≥2 CTAs/SM, split-KV CTAs ≈ 2–8× SM count — impact: ★★★★☆, effort: low-medium
The current kernel launches 64 CTAs of 96 active threads (12 resident warps/SM best case, 8.3% achieved). References: XQA pins `MIN_BLOCKS_PER_SM=4` at 256 threads; FlashInfer GEMV launches 128 threads minimum and splits KV until `occupancy × num_SM` CTAs (min 256-token chunks); FA2's heuristic splits until wave-efficiency ≥0.85×best (threshold: ≥0.8×num_SMs without splitting), max 128 splits; XQA targets `kTargetWaveFactor = 8` waves with a `sqrt(8×blocks)` cap to bound merge cost. For our shape (4 kv-heads, batch 1): plan ~32–128 CTAs (4–32 per kv-head) at 128–256 threads, and size chunks so all 16 SMs get 2–4 CTAs. Sources: A1–A5.

### 4. 16-byte cp.async.cg for every KV access, contiguous per-lane rows — impact: ★★★★☆, effort: low (audit)
FA2: `SM80_CP_ASYNC_CACHEGLOBAL<uint128_t>` (bypasses L1); FlashInfer: `cp_async<16>` `.cg`; XQA: 16-byte `Qk_vec_m` for all dtypes (fp8: 16 values per vector); llama.cpp vec kernel: 16-byte; jetson-mem-bench reference kernel: 16-byte + unroll. With 128–256 threads and 16 B/thread, a 64-row × 256 B fp8 K stage is issued as 1024–2048 16-byte transactions — one full stage per instruction sweep. Verify the current kernel issues ≥16 B per thread per stage *contiguously per row* and that pages ≥64 keep ≥1 full row per issue group (page 16 → 4 rows/page: 4 CTAs' worth of rows land in one 4 KB DRAM burst).

### 5. Deepen the cp.async ring to 3–4 stages and overlap softmax/exp2 with the load — impact: ★★★★☆, effort: medium
FlashInfer's GEMV uses only `NUM_STAGES_SMEM = 2` on CC≥8 ([utils.cuh dispatch](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.0.post1/include/flashinfer/utils.cuh)) — with per-token 512 B stages that is the latency-coverage failure mode; FA2 double-buffers KV; llama.cpp targets `nstages_target = 2` but with 128-row staged tiles (≈64 KB/stage equivalent). With 64-row stages, 3–4 stages × (K+V) 32–64 KB fits Orin's 163 KB at 1 CTA/SM (or 2 stages at 2 CTAs/SM); PTX `cp.async.commit_group`/`wait_group N` gives the producer-consumer overlap without full barriers every token. Sources: A1–A5 + PTX doc.

### 6. Dequant placement: fp8→bf16 once per value on the consumer side; fold per-channel K scales into Q — impact: ★★★☆☆, effort: medium
sm_87 has no fp8 HW cvt or mma (CC 8.9/9.0 only) — every fp8 value needs software conversion (FlashInfer `fast_dequant_f8f16x4`: prmt + shift/mask + 2×HMUL2 per 4 values). Options, in cost order: (a) fold per-channel K scales into Q once per step (KIVI/SageAttention pattern, companion arxiv summary) so the inner loop is pure cvt→HMMA with zero multiplies; (b) convert each 16-byte vector **once** per stage into registers staged for both QK and (after softmax) PV — never re-convert; (c) with Orin's spare smem, repack fp8→bf16 in smem once per stage and run both GEMMs on clean bf16 tiles (FlashInfer has this "repack" staging path for prefill; XQA-style int8 KV keeps the LUT approach). Sources: A1, A4, companion arxiv summary (KIVI, SageAttention, SnapMLA consumer-side rule).

### 7. L2 policy on the KV stream: evict_first + optional L2::128B/256B prefetch; Q/scales evict_last — impact: ★★★☆☆, effort: low
KV is single-use streaming data; on a 4 MB L2 it should be tagged evict-first so it doesn't thrash Q, scales, page tables, and the merge buffers. Mechanisms on sm_87: `createpolicy` + `cp.async`/`ld.global` `.level::cache_hint` (PTX ISA 7.4, sm_70+), `.level::prefetch_size` (sm_80+), `cudaStreamSetAttribute` access-policy window (CC 8.0+), `cudaCtxResetPersistingL2Cache` after use. FlashInfer's decode path applies no evict policy to the KV stream (verified gap in the baseline); FlashInfer's FP16-QK path does use `.L2::128B` prefetch — evidence the hint is profitable on this class of kernel.

### 8. Merge: one wave of partials + last-CTA/fused combine, not a serialized second launch — impact: ★★★☆☆, effort: low-medium
With splits fixed by mechanism 3, partials are tiny; FA2's combine kernel (kBlockM=4, log2 splits, single launch) and FlashInfer's `MergeStates` are both separate kernels, and FlashInfer has **no PDL on Orin** (`device_support_pdl` requires CC ≥ 9) — so on sm_87 every extra launch is a hard serialization at decode cadence. Options: grid-sync-free last-CTA combine (atomic counter + the j-ordered LSE merge), or fold combine into the next layer's prologue. Sources: A2 (combine kernel), companion summary (no PDL), [flash_fwd_launch_template.h](https://github.com/Dao-AILab/flash-attention/blob/main/csrc/flash_fwd_launch_template.h).

### 9. Measurement: jetson_clocks + `--clock-control none`; MAXN; keep the CPU off the bus — impact: ★★☆☆☆ (measurement validity), effort: trivial
ncu cannot lock clocks on GA10b — its reported durations inherit DVFS state; NVIDIA's own guidance is external locking + `--clock-control none`. Run MAXN (`nvpmodel -m 0`), pin with `jetson_clocks`, and treat ncu ratios (not wall clock) as the kernel instrument (repo discipline). Unified-memory hazard: CPU work during decode competes for the same 204.8 GB/s. Sources: ncu guide §Clock Control, jetson-mem-bench, Arya & Simmhan.

### 10. Target: 120–165 GB/s sustained (60–80% of 204.8); >100 GB/s is the floor for "done" — impact: calibration, effort: none
jetson-mem-bench's STREAM-class expectation on Orin is 60–80% of theoretical with 16-byte vectorized access; a decode kernel that keeps 32–64 KB stages in flight per CTA across 2–4 CTAs/SM is the same access pattern at larger granularity. There is **no published Orin decode-attention achieved-GB/s** (negative result, confirmed in the arxiv companion summary) — the first measurement will be novel; use ncu `dram__bytes.sum.per_second` ratios within a single run.

## Gaps and caveats
1. **LPDDR5 read-vs-write asymmetry on Orin: unverified.** Search engine was down all session; no accessible primary source found. Decode is read-dominated (writes ≈ O only), so impact is second-order, but the claim should not be repeated without a source.
2. **XQA Ampere kernel geometry: closed source** (cubins only). Everything above about XQA is from the runner/heuristics/support gates in-tree + the blog; the inner loop (mma shapes, cp.async depth, register blocking) is not public.
3. **No Orin achieved-bandwidth number for FlashInfer decode** exists in any public source (consistent with the arxiv summary's negative result). The 4–5× figure remains our own measurement.
4. **Derived, not sourced**: the 42.5 TFLOPS fp16-TC figure (16 SM × 2048 FLOP/clk/SM × 1.3 GHz) and the per-mechanism impact stars (roofline arithmetic); Little's-law-style latency-coverage argument is qualitative (no measured LPDDR5 latency source this session).
5. CUTLASS's FMHA blog post URL is dead (404); ex41 is cited from source instead.
